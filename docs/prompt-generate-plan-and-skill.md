# Промпт: згенерувати план реалізації та skill з roadmap

Скопіюй усе нижче і віддай агенту (Claude Code) у корені репозиторію, поруч з `roadmap-coin-collection.md`.

---

Проаналізуй файл `roadmap-coin-collection.md` у корені репозиторію. Це узгоджений план персонального сайту-колекції (монети, пізніше ОВДП) на Next.js + Supabase + Vercel. Твоя задача — розкласти цей roadmap на конкретний план реалізації та зафіксувати правила роботи над репозиторієм у вигляді skill. Нічого з коду проєкту поки не пиши — лише плануючі файли.

## Крок 0 — архітектурний підхід і файлова структура

Перед розкладанням на кроки визнач і задокументуй **архітектурний підхід** проєкту. Roadmap вже визначає домени на рівні БД (окремі Postgres-схеми: `coins`, `bonds`, спільне через `public.profiles`) — файлова структура коду має дзеркалити цей поділ, а не розсипатись на наскрізні `components/`, `hooks/`, `utils/` папки, спільні для всіх фіч.

Орієнтуйся на **feature-based / vertical slice** підхід (той самий принцип, що й vertical slice modular monolith у C#, адаптований під Next.js/TypeScript): кожен домен (`coins`, `wishlist`, пізніше `bonds`) — самодостатня "фіча"-папка зі своїми компонентами, server actions/queries, Zod-схемами валідації, типами й тестами всередині. Спільне між фічами (auth, UI-кит, клієнт Supabase) — виносити в окремий явний shared-шар, не розмазувати по фічах.

Оціни, чи є для Next.js App Router (2026) усталеніший/сучасніший варіант цього підходу, ніж класичний "feature folders" (наприклад, colocation за конвенціями App Router, screaming architecture, або гібрид) — обери те, що найкраще лягає на App Router і поясни чому.

Результат цього кроку — файл `/plan/00-architecture-and-structure.md`, що фіксує:
- Обраний архітектурний підхід і коротке обґрунтування (чому саме він, а не альтернативи)
- Дерево директорій верхнього рівня з поясненням призначення кожної (де живуть фічі, де shared-шар, де тести)
- Правило: що вважається "витоком" між фічами (наприклад, пряма імпортація компонента однієї фічі в іншу) і як цього уникати
- Відповідність цієї структури схемам БД з roadmap (`coins` ↔ фіча `coins`, і так далі)

Ця структура — обов'язкова для всіх наступних кроків плану і має потрапити в skill (Крок 2) як правило, якого агент дотримується при написанні коду.

## Крок 1 — план реалізації

Створи директорію `/plan/` (якщо немає) і по одному `.md` файлу на кожен пункт/розділ з roadmap (MVP-пункти 1–6, архітектура БД, тестування, UI/навігація, хостинг) — нумеруючи від `01` і далі, одразу після `00-architecture-and-structure.md` з Кроку 0. Нумеруй файли за логічним порядком реалізації (враховуй залежності — наприклад, авторизація й архітектура БД мають йти раніше за CRUD монет, CRUD раніше за dashboard).

Формат назви: `NN-коротка-назва.md`, наприклад: `01-db-architecture.md`, `02-auth.md`, `03-coins-schema-and-crud.md`, `04-coins-view-search.md`, `05-import-export.md`, `06-wishlist.md`, `07-dashboard.md`, `08-ui-navigation.md`, `09-testing-setup.md`, `10-hosting-deploy.md` — але підлаштуй під реальний зміст roadmap, не копіюй сліпо цей список. Кожен крок, що зачіпає код, має явно посилатись на `00-architecture-and-structure.md` і слідувати визначеній там структурі — які фічі-папки зачіпаються, чи є новий shared-код.

Кожен файл плану має містити:

```markdown
# NN. Назва кроку

## Статус
не розпочато | у роботі | завершено

## Зв'язок з roadmap
Короткий опис, з якого розділу roadmap.md походить цей крок

## Залежності
Список файлів /plan/, які мають бути "завершено" перед стартом цього кроку (або "немає")

## Підзадачі
- [ ] конкретна технічна підзадача
- [ ] ще одна
- [ ] ...

## Acceptance criteria
(перенеси відповідні acceptance criteria з roadmap.md для цього розділу дослівно, чекбоксами)

## Нотатки з реалізації
(порожньо на старті — цей блок агент заповнює під час роботи: рішення, компроміси, що змінилось відносно плану)
```

## Крок 2 — skill з правилами репозиторію

Створи skill (структура `SKILL.md` за стандартом Anthropic skills — з фронтматером `name` і `description`, і тілом-інструкцією), який має **завжди** підвантажуватись при роботі над цим репозиторієм. Розмісти його там, де агент зазвичай шукає project-скіли для цього репо (наприклад `.claude/skills/project-rules/SKILL.md` — якщо є інше прийняте місце в цьому середовищі, використай його).

Skill повинен містити такі правила:

### Технічні правила репозиторію (витягни з roadmap.md і 00-architecture-and-structure.md, не вигадуй нового)
- Обраний архітектурний підхід (feature-based / vertical slice) з `/plan/00-architecture-and-structure.md` — новий код лягає у відповідну фіча-папку, без прямих імпортів між фічами повз shared-шар
- Стек, схеми БД, правило міграцій "тільки через Supabase CLI, ніяких ручних правок схеми в Supabase Dashboard на проді"
- Модульний моноліт: домени в окремих Postgres-схемах, без прямих FK між доменами крім `public.profiles`
- Обов'язкові інтеграційні тести (Vitest, локальний `supabase start`) для кожної фічі з бек-логікою
- Правила UI/палітри з roadmap (ролі кольорів, навігація, перемикач вигляду) — не відступати без узгодження

### Правила процесу роботи (головне)
- Агент працює **над одним кроком з `/plan/` за раз**, у порядку номерів, з урахуванням залежностей — не перескакує наперед і не робить кілька кроків паралельно в одній сесії
- Перед стартом кроку — читає відповідний `/plan/NN-*.md` повністю
- Під час роботи — відмічає підзадачі як виконані (`[x]`) по мірі просування, а не одним махом наприкінці
- Після виконання acceptance criteria кроку і проходження тестів — заповнює блок "Нотатки з реалізації" (що зроблено, чим відрізняється від початкового плану, якщо відрізняється) і **змінює "Статус" файлу на "завершено"**
- Один крок = один завершений і "закритий" `.md` файл. Наступний крок не починається, поки поточний явно не позначено завершеним
- Якщо під час роботи з'ясовується, що крок треба розбити на менші — агент оновлює `/plan/`, а не мовчки відхиляється від нього

Після виконання Кроку 1 і Кроку 2 — виведи список створених файлів і коротко підсумуй порядок кроків, який ти визначив, і чому саме такий.
