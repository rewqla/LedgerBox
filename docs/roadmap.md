# Roadmap: Персональний сайт колекції (Монети / ОВДП)

## Технічний стек

| Компонент | Рішення |
|---|---|
| Фронтенд + бекенд | Next.js (App Router, API routes / server actions) |
| База даних | Supabase (Postgres) |
| Авторизація | Supabase Auth |
| Файлове сховище (фото монет) | Supabase Storage |
| Хостинг | Vercel (деплой з git) |
| Локальна розробка | Supabase CLI (`supabase start`) — піднімає Postgres/Auth/Storage в Docker локально |

Цільовий бюджет MVP: 0 грн/міс. Використовуємо безкоштовні тарифи сервісів, доки їхніх лімітів достатньо для персонального використання.

### Файлове сховище — деталі

Окремий приватний bucket `coin-photos` (не публічний). Доступ — через RLS-політики на `storage.objects`: користувач повинен бути авторизований і мати запис у `public.profiles`.

Колекція **спільна для всіх користувачів з доступом**, тому `owner_id` / `user_id` у монетах та фотографіях не використовується.

У таблиці `coins` зберігаються тільки шляхи до двох можливих фото:
- `obverse_photo_path` — аверс, nullable
- `reverse_photo_path` — реверс, nullable

Окремої таблиці `coin_photos` у MVP немає. Максимум два фото забезпечується самою структурою таблиці.

Рекомендована структура Storage:

```text
coin-photos/
  {coin_id}/
    obverse.webp
    reverse.webp
```

URL для відображення не зберігається в БД — signed URL з обмеженим часом дії генерується на льоту.

**Два способи додати фото:**
1. Завантаження з локального ПК
2. Імпорт за URL — бекенд сам завантажує файл, обробляє його і зберігає копію у bucket, щоб не залежати від зовнішнього джерела

**Єдине правило для фото: кінцевий файл у Storage не може перевищувати 1 MB.**

Base64 у Postgres не використовується. У БД зберігається лише шлях до файлу, сам файл — у Supabase Storage.

Пайплайн обробки фото:

```text
Оригінал
  ↓
перевірка та декодування
  ↓
resize до розумного максимального розміру (~1200–1600px по довшій стороні)
  ↓
конвертація у WebP
  ↓
компресія
  ↓
якщо > 1 MB — додаткове зменшення quality / dimensions
  ↓
фінальний файл ≤ 1 MB
  ↓
Supabase Storage
```

Для локального файлу первинна обробка виконується на клієнті перед upload. На рівні bucket також задається максимальний розмір файлу 1 MB як додатковий захист.

Для імпорту за URL обробка виконується на бекенді. Обов'язкові перевірки:
- дозволені тільки `http` / `https`
- заборона localhost, private та link-local адрес
- timeout на завантаження
- обмеження кількості redirect
- обмеження максимального розміру завантажуваних даних
- MIME / content validation
- файл повинен реально декодуватися як зображення
- після resize / compression фінальний файл має бути ≤ 1 MB

## MVP — Перша ітерація

Мета MVP: робочий приватний сайт для ведення **спільної колекції монет** із базовим адмініструванням. Доступ мають тільки вручну дозволені користувачі з `public.profiles`. ОВДП — **не входить** в MVP.

### 1. Авторизація

**Опис:** доступ до сайту (перегляд і редагування) мають лише авторизовані користувачі, які присутні в `public.profiles`. Усі такі користувачі рівноправні й працюють з однією спільною колекцією. Публічного доступу немає; read-only режим — можливий у майбутньому.

**Acceptance criteria:**
- [ ] Вхід через email+пароль (Supabase Auth)
- [ ] Без входу — недоступні жодні дані (редірект на сторінку логіну)
- [ ] Сесія зберігається (не треба логінитись щоразу)
- [ ] Реєстрація нових користувачів вимкнена; доступ додається вручну
- [ ] Наявність auth-акаунта сама по собі не дає доступу — потрібен запис у `public.profiles`
- [ ] Користувач не може самостійно додати себе або інших у `public.profiles`
- [ ] RLS-політики перевіряють наявність `auth.uid()` у `public.profiles`
- [ ] Усі користувачі з `profiles` мають однаковий доступ до спільної колекції
- [ ] У доменних таблицях немає `owner_id`

### 2. Розділ "Монети" — перегляд і пошук

**Опис:** основний екран колекції з можливістю перемикати вигляд, шукати та фільтрувати монети.

**Поля монети (MVP):**
- `name` — назва
- `mint_year` — рік карбування, необов'язково
- `acquired_at` — дата придбання / потрапляння до колекції
- `purchase_amount` — сума придбання
- `purchase_currency` — валюта придбання (`UAH`, `USD`, `EUR`; список можна розширити пізніше)
- `fx_usd_rate` — зафіксований курс для перерахунку покупки в USD на дату придбання
- `category_id` — категорія (розширюваний довідник, не хардкод)
- `is_precious` — дорогоцінний метал: так/ні
- `precious_metal_type` — тип дорогоцінного металу, nullable (`gold`, `silver`, `platinum`)
- `precious_metal_weight_g` — вага дорогоцінного металу в грамах, nullable
- `obverse_photo_path` — фото аверсу, nullable
- `reverse_photo_path` — фото реверсу, nullable
- `notes` — нотатки, необов'язково
- `created_at`
- `updated_at`

`purchase_amount_usd` окремо не зберігається, якщо його можна однозначно обчислити з `purchase_amount`, `purchase_currency` та `fx_usd_rate`.

Правила для дорогоцінного металу:
- якщо `is_precious = false`, `precious_metal_type` і `precious_metal_weight_g` мають бути `NULL`
- якщо `is_precious = true`, тип металу та вага заповнюються
- окремого довідника `metals` у MVP немає

**Acceptance criteria:**
- [ ] Список усіх монет у двох режимах відображення: картки (фото + назва + рік) і таблиця
- [ ] Перемикання вигляду зберігається (localStorage / налаштування користувача)
- [ ] Пошук за назвою
- [ ] Фільтр за роком, категорією та дорогоцінним металом
- [ ] Клік на монету відкриває детальну картку з усіма полями
- [ ] Монета може мати 0, 1 або 2 фото: окремі слоти для аверсу та реверсу
- [ ] Третє фото додати неможливо, оскільки окремої галереї / таблиці фото в MVP немає
- [ ] Кожен кінцевий файл фото у Storage ≤ 1 MB

### 3. Розділ "Монети" — адміністрування (CRUD)

**Acceptance criteria:**
- [ ] Додати монету через форму з усіма MVP-полями
- [ ] Завантажити фото аверсу та/або реверсу локальним файлом
- [ ] Імпортувати фото за URL через захищений backend endpoint
- [ ] Редагувати монету
- [ ] Замінити або видалити окремо фото аверсу / реверсу
- [ ] При заміні фото старий файл коректно видаляється зі Storage
- [ ] При видаленні монети її файли також видаляються зі Storage
- [ ] Видалити монету з підтвердженням
- [ ] Керування категоріями: додати / перейменувати категорію
- [ ] Початкові категорії: "українська", "закордонна"
- [ ] Довільні нові категорії додаються без зміни коду

### 4. Dashboard / статистика

**Опис:** окрема сторінка з підсумковими цифрами по колекції. У MVP — фіксований набір базових віджетів; повна конфігурованість (drag&drop, вибір метрик) — у Future Roadmap.

**Acceptance criteria:**
- [ ] Загальна кількість монет
- [ ] Загальна сума вкладень у вихідних валютах / грн та в еквіваленті USD за зафіксованим курсом на дату придбання
- [ ] Розбивка за категоріями
- [ ] Розбивка дорогоцінні / звичайні
- [ ] Список останніх доданих монет
- [ ] Графік накопичених вкладень у часі за `acquired_at`
- [ ] Витрати за роками придбання
- [ ] Гістограма монет за `mint_year`

### 5. Розділ "Бажанки" (вішлист)

**Опис:** список монет, які хочеться придбати. Мінімальний функціонал у MVP.

**Acceptance criteria:**
- [ ] Додати запис: назва монети (обов'язково), URL на товар (обов'язково), орієнтовна середня ціна (опційно) — без фото, wishlist навмисно текстовий
- [ ] Список бажанок окремо від основної колекції
- [ ] Видалити / позначити як "придбано" (просто прибирає зі списку)
- [ ] Перенесення в колекцію одним кліком — бажано, але не критично для MVP

### 6. Розділ "Монети" — імпорт / експорт

**Опис:** можливість вивантажити колекцію монет і завантажити її назад для перенесення, резервного копіювання даних або масового редагування поза UI. Це окремий користувацький import/export; автоматичні інфраструктурні backup-и описані нижче.

**Acceptance criteria:**
- [ ] Експорт усієї спільної колекції у файл
- [ ] Формат визначити перед реалізацією; базовий кандидат — JSON, CSV можна додати окремо для табличного редагування
- [ ] Імпорт монет із файлу назад у колекцію
- [ ] Валідація імпортованих даних перед записом у БД
- [ ] Некоректні записи не ламають імпорт повністю; показується звіт, що саме не імпортовано
- [ ] Фото не входять в import/export MVP — тільки текстові поля і шляхи не використовуються як переносимі файли
- [ ] Перед реалізацією визначити поведінку повторного імпорту / дублювання записів

## Future Roadmap (після MVP)

Без прив'язки до дат — пріоритезуємо, коли дійдемо.

1. **Розділ ОВДП** — окремий розділ з обліком облігацій (номінал, ставка, дата погашення, купонні виплати)
2. **Автоматичне підтягування курсу дорогоцінних металів** (срібло/золото/платина) для переоцінки монет за вагою
3. **Поточна ринкова ціна монети** — можливість зберігати / підтягувати поточну оцінку та джерело ціни:
   - `current_market_price`
   - `current_market_currency`
   - `current_market_fx_usd_rate`
   - `market_price_updated_at`
   - `market_price_source_url`
4. **Dashboard-віджет "Куплено / Поточна вартість"** — для монет, де заповнені і дані покупки, і поточна ринкова оцінка:
   - вкладено
   - поточна оцінена вартість
   - абсолютна різниця
   - результат у %
   - кількість оцінених монет / загальна кількість монет
5. **Інтеграція зовнішніх джерел актуальної ціни монет** — де можливо, каталоги / API для автоматичного оновлення `current_market_price`
6. **Конфігурований dashboard** — користувач сам обирає, які віджети показувати і в якому порядку
7. **Перенесення з бажанок у колекцію** одним кліком зі збереженням назви; фото та решта полів довносяться вручну
8. **Розширювані довільні розділи** — можливість додавати нові типи колекцій (не тільки монети) без зміни коду
9. **Публічний read-only режим** — можливість поділитися колекцією посиланням без права редагування

## Архітектура бази даних (модульний моноліт)

Одна Postgres-база (Supabase), але домени ізольовані окремими **схемами**, а не звалені в один `public`:

| Схема | Призначення |
|---|---|
| `auth` | Керується Supabase (сесії, користувачі) |
| `public` | Спільне: `profiles` (allow-list користувачів з доступом); у майбутньому — спільні довідники на кшталт курсів валют |
| `coins` | `coins`, `categories`, `wishlist_items` |
| `bonds` *(майбутнє)* | Все про ОВДП — власні таблиці, без прямих FK на `coins` |

Правила:
- колекція одна спільна для всіх користувачів з `public.profiles`
- `owner_id` у `coins`, `categories`, `wishlist_items` не використовується
- домени не мають прямих зв'язків один з одним
- спільний контроль доступу здійснюється через `public.profiles`
- `wishlist_items` живе всередині схеми `coins`, бо стосується виключно монет

### Базова модель MVP

```text
public.profiles

coins.coins
  id
  name
  mint_year
  acquired_at
  purchase_amount
  purchase_currency
  fx_usd_rate
  category_id
  is_precious
  precious_metal_type
  precious_metal_weight_g
  obverse_photo_path
  reverse_photo_path
  notes
  created_at
  updated_at

coins.categories
  id
  name
  created_at
  updated_at

coins.wishlist_items
  id
  name
  url
  expected_price
  created_at
  updated_at
```

Окремих `coin_photos` та `metals` у MVP немає.

**Міграції — обов'язково, без винятків:**
- схема БД визначається тільки SQL-файлами в `supabase/migrations/`, під git
- створення: `supabase migration new <назва>`
- застосування: `supabase db push` локально / автоматично через CI при мержі в `main`
- ручні зміни схеми через Supabase Dashboard UI на production — заборонені
- конфігурація локального / remote Supabase, яку можливо тримати як код, зберігається в репозиторії

**Acceptance criteria:**
- [ ] Кожен домен (`coins`, `bonds`) — окрема Postgres-схема
- [ ] Жодних прямих FK між доменними схемами
- [ ] Спільна колекція не містить `owner_id`
- [ ] RLS для доменних таблиць перевіряє membership через `public.profiles`
- [ ] Уся історія змін схеми — у вигляді послідовних міграцій у git, відтворювана з нуля
- [ ] Локальний старт (`supabase start`) автоматично застосовує всі міграції з `supabase/migrations/`
- [ ] CI/CD автоматично застосовує нові міграції на production БД при мержі в `main` (GitHub Actions + Supabase CLI), без ручного кроку

## Тестування

**Acceptance criteria:**
- [ ] Локальний Supabase-стек (`supabase start`, підіймає Postgres/Auth/Storage в Docker) використовується і для розробки, і для тестів
- [ ] Міграції прогоняються автоматично на тестовій БД перед запуском тестів
- [ ] Інтеграційні тести (Vitest) викликають server actions / API route handlers напряму, перевіряють і відповідь, і фактичний стан у БД (не моки Supabase-клієнта)
- [ ] Тести CRUD монет
- [ ] Тести CRUD категорій
- [ ] Тести CRUD бажанок
- [ ] Тести RLS: неавторизований користувач не має доступу; auth-користувач без `profiles` не має доступу; користувач із `profiles` має доступ до спільної колекції
- [ ] Тести фото: 0/1/2 фото, окремі аверс/реверс, третій слот відсутній
- [ ] Тести обробки фото: фінальний файл ≤ 1 MB
- [ ] Тести URL-import: блокування приватних адрес, timeout / size limit, невалідне зображення
- [ ] Тести cleanup Storage при заміні фото та видаленні монети
- [ ] Тести запускаються в CI (GitHub Actions) на кожен PR, merge у `main` блокується при їх падінні

## UI / Дизайн

### Навігація

Бічна панель, розкривні (dropdown) розділи-домени — кожен домен може мати власні підрозділи:

- **Монети** (розкривний)
  - Колекція
  - Бажанки
- **ОВДП** (розкривний, поки заглушка з міткою "скоро", підрозділи визначимо ближче до реалізації)
- **Дашборд** (окремий верхній пункт, загальна статистика — не прив'язаний лише до монет)

Активний пункт підсвічується акцентним кольором. Layout спільний (Next.js), при переході між розділами перемальовується лише контентна область, без білого екрана.

**Acceptance criteria:**
- [ ] Бічна навігація з розкривними доменами (Монети → Колекція/Бажанки)
- [ ] Пункт ОВДП присутній, візуально приглушений, з міткою "скоро", некликабельний до реалізації
- [ ] Дашборд — окремий пункт верхнього рівня
- [ ] Активний розділ і підрозділ візуально виділені (акцентний фон)

### Перемикач вигляду (картки / список)

- [ ] Дві кнопки-іконки (сітка / список) над списком монет
- [ ] Активний режим підсвічений акцентним кольором
- [ ] Вибір зберігається між сесіями

### Палітра

Мінімалістична, кольори за ролями, не за декором:

| Роль | Колір | Де використовується |
|---|---|---|
| Акцент | синій (`accent`) | Активна навігація, кнопки, посилання — один акцент на весь інтерфейс |
| Дорогоцінний метал | бурштиновий (`amber`) | Виключно бейдж дорогоцінного металу на монеті |
| Структура | сірий/нейтральний | Картки, фон, таблиця, бордери, звичайні монети без бейджа |

Коли додасться ОВДП — під нього виділяється власний окремий акцентний колір, щоб розділи відрізнялись візуально з першого погляду.

**Типографіка:** заголовки розділів — легкий serif (`font-voice`) для "колекційного" відчуття, весь інший текст (таблиці, форми, навігація) — звичайний sans-serif.

### Автоматичні резервні копії

Ручний backup як регулярний процес не використовується. Резервне копіювання запускається автоматично через GitHub Actions за розкладом.

**Стратегія:**

```text
Щодня:
  PostgreSQL dump

Щотижня:
  PostgreSQL dump
  +
  backup bucket `coin-photos`
  ↓
  archive
  ↓
  збереження як backup artifact / у визначене backup-сховище
```

Орієнтовна retention policy:
- daily DB backup — 30 днів
- weekly full backup (DB + Storage) — 4 тижні або довше, якщо дозволяє вибране сховище

Backup БД та backup Storage вважаються двома окремими частинами одного повного backup. Наявність DB dump без файлів `coin-photos` не вважається повним резервним копіюванням колекції.

- [ ] Міграції застосовуються автоматично через CI/CD
- [ ] DB backup запускається автоматично щодня
- [ ] Повний backup DB + `coin-photos` запускається автоматично щотижня
- [ ] Backup workflow працює без ручних дій
- [ ] Секрети backup workflow зберігаються тільки в GitHub Secrets / відповідному secret storage
- [ ] Є retention policy, яка автоматично видаляє застарілі backup-и
- [ ] Процедура restore описана і хоча б один раз перевірена на тестовому середовищі
