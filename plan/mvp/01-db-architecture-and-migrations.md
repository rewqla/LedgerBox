## Підзадачі
- [ ] Ініціалізувати `supabase/` конфігурацію для локальної розробки й CI
- [ ] Створити початкові міграції для схем `public`, `coins` і зарезервувати підхід для `bonds`
- [ ] Створити таблицю `public.profiles` для allow-list доступу
- [ ] Створити таблиці `coins.coins`, `coins.categories`, `coins.wishlist_items`
- [ ] Додати обмеження даних для дорогоцінних металів і фото-полів
- [ ] Додати RLS-політики для доменних таблиць через membership у `public.profiles`
- [ ] Зафіксувати seed/bootstrapping початкових категорій `"українська"` і `"закордонна"`
- [ ] Описати безпечний bootstrap першого користувача без фіксованих логіна/пароля в міграціях
- [ ] Підготувати CI/CD шлях для автоматичного застосування міграцій
- [ ] Додати або оновити тести для SQL-обмежень, схем і RLS, які з'являються в цьому кроці

## Acceptance criteria
- [ ] Кожен домен (`coins`, `bonds`) — окрема Postgres-схема
- [ ] Жодних прямих FK між доменними схемами
- [ ] Спільна колекція не містить `owner_id`
- [ ] RLS для доменних таблиць перевіряє membership через `public.profiles`
- [ ] Уся історія змін схеми — у вигляді послідовних міграцій у git, відтворювана з нуля
- [ ] Перший користувач не зашивається в міграції як фіксований `admin/admin`; bootstrap виконується окремо й безпечно
- [ ] Локальний старт (`supabase start`) автоматично застосовує всі міграції з `supabase/migrations/`
- [ ] CI/CD автоматично застосовує нові міграції на production БД при мержі в `main` (GitHub Actions + Supabase CLI), без ручного кроку
