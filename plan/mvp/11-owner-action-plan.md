## План дій саме для вас

Цей документ стосується саме вас. Це не технічний план для агента і не backlog розробки, а окремий список дій, які маєте виконати ви як власник проєкту.

Агент може:

- підготувати код
- створити міграції
- написати документацію
- згенерувати workflows
- підготувати шаблони конфігурації

Але агент не повинен вважати виконаними ті кроки, де потрібні ваші акаунти, ваші секрети, ваші рішення або ваш ручний доступ до зовнішніх сервісів.

## До початку реалізації

- Створити GitHub-репозиторій для проєкту, якщо його ще немає
- Встановити локально:
  - Node.js LTS
  - Docker Desktop
  - Supabase CLI
- Створити Supabase-проєкт
- Створити Vercel-проєкт
- Визначити, хто буде першим користувачем системи і яку email-адресу він матиме
- Створити файл `.env.local` і заповнити його власними значеннями на основі `.env.example`

## Під час реалізації

- Давати відповіді на всі відкриті питання з активного кроку плану
- Створити першого користувача через Supabase Auth admin flow, CLI або dashboard admin panel
- Додати цього користувача в `public.profiles` після появи міграцій або через підготовлений bootstrap flow
- Перевіряти локально критичні сценарії, якщо потрібне ручне підтвердження UX або бізнес-поведінки
- Не передавати секрети через коміт у репозиторій

## Перед деплоєм

- Додати секрети й змінні середовища в хостинг і CI
- Підключити GitHub до Vercel
- Підключити GitHub Secrets для CI/CD і backup workflows
- Створити безпечні значення для всіх паролів, токенів і service-role ключів
- Переконатися, що для production, preview і development задані коректні env variables

## Після деплою

- Перевірити production login першим користувачем
- Переконатися, що self-signup вимкнений
- Перевірити, що міграції застосовуються автоматично
- Перевірити, що backup workflows запускаються за розкладом
- Перевірити процедуру restore на тестовому середовищі

## Яку конфігурацію ви маєте зробити самі

### Локально

- Створити файл `.env.local` і заповнити його власними значеннями
- Не комітити `.env.local`, `.env`, `.env.production` та будь-які файли з реальними секретами

### Supabase

- Створити проєкт
- Взяти:
  - `NEXT_PUBLIC_SUPABASE_URL`
  - `NEXT_PUBLIC_SUPABASE_ANON_KEY`
  - `SUPABASE_SERVICE_ROLE_KEY`
- Вимкнути self-signup, якщо це не буде зроблено кодом/конфігурацією автоматично
- Окремо створити першого користувача без дефолтного пароля в репозиторії

### Vercel

- Створити production project
- Додати ті самі env variables, які потрібні застосунку
- Переконатися, що вони задані для потрібних середовищ: Production, Preview, Development

### GitHub

- Додати secrets для CI/CD і backup jobs
- Захистити `main`, щоб merge блокувався при падінні тестів

## Які секрети ви не повинні комітити

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- `SUPABASE_SERVICE_ROLE_KEY`
- `SUPABASE_ACCESS_TOKEN`
- backup credentials
- будь-які токени Vercel або GitHub, якщо вони потрібні automation flows

## Як це трактувати під час роботи

- Якщо якийсь пункт із цього файлу ще не зроблено, агент не має мовчки вважати його виконаним
- Якщо для наступного кроку потрібна ваша дія, агент має прямо сказати вам про це
- Якщо потрібні секрети або зовнішні акаунти, ви маєте надати їх через безпечну конфігурацію, а не через коміт у репозиторій
